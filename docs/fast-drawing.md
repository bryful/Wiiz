# 高速描画の撤回と表示崩れ修正

2026-10-20に報告されたちらつき・画面崩れ・宝箱後の残像により、Wiz1用の高速描画パッチを撤回しました。
現在の実行コードはROMのコピーにもパッチを適用しません。元ROMをそのまま既存binjnesで実行します。
保存済みの`fast-drawing.txt`がONでも読み込まず、Qメニューからも再有効化できません。
撤回時点の安定版では描画速度を通常に戻しました。
その後のユーザー要望により、元の描画を完走させた上で全体を倍速にし、音楽とキーリピートを分離する機能を追加しました。
現在の仕様は[turbo.md](turbo.md)を参照してください。この文書は旧パッチ撤回時の記録です。

## 問題の経路

撤回した実装は、`$C307`のフレーム待ちを未使用領域の接続コードへ変更し、原作のNMI処理`$C06B`へ直接入っていました。

- 強制ブランクを伴う転送がVBlank以外でも実行され、走査途中の描画を中断し得ました。
- 通常の`$C147-$C157`に含まれる、`$1A`以降の未使用OAMをY=$F0へ隠す処理が抜けていました。
  戦闘スプライトの残像と整合します。ただし報告された宝箱操作そのものの再現確認は別途必要です。
- 元のフレーム待ちには描画以外の役割もあり、一部だけを呼び出す方法は安全ではありませんでした。

城メニューが完成した時点や、迷宮の最後の静止画が一致しても、走査中・画面切替中の正しさは検証できません。
前回の検証範囲が不足していたため、完成画像の一致と速度短縮だけで採用した判断を撤回します。

## 修正

- SessionのROM書換・接続コード挿入・実行時切替をすべて削除。
- ON設定を無視し、「Drawing: original (stability fix)」として通常描画を強制。
- 原作の待ち・未使用スプライト消去・転送・背景復元を含む経路へ復帰。
- セーブの形式と保存先は従来どおり。ユーザーの既存セーブを削除・巻き戻ししません。

旧版を終了してから修正版を起動してください。旧版の途中状態を継続するためのステート保存は使用していません。

## 検証

```powershell
python tests/check_native_drawing.py output/native-build/windows-vs/Release/wiiz.exe
python tests/check_native_input.py output/native-build/windows-vs/Release/wiiz.exe
python tests/check_native_core.py output/native-build/windows-vs/Release/wiiz.exe
```

`--drawing-check ROM [入力スクリプト [フレーム数 [検証用セーブフォルダ]]]`は、
Session経由の実行と、ディスク上の未改変ROMから独立して初期化したbinjnes参照実行を比較します。
最終画面だけではなく、各フレームの256×240全画素と全音声サンプルを比較します。

- Wiz1の起動・城まで900フレーム、および初期戦士を編成して迷宮へ進む4,300フレームで、
  切替途中も含む全画素・音声サンプルが参照実行と一致。
- 旧smoke引数`fast`を渡しても原作描画のまま。ROMファイルのハッシュも不変。
- 3作品の起動・音声生成・8KiBバッテリーセーブ往復・RAM保持リセット、Q/Zメニュー・終了操作を確認。
- ユーザーセーブの調査はoutput内のコピーだけを使用。
- 初期6人で迷宮へ入り、人型5体との戦闘から探索画面へ戻る入力を`tests/replays/wiz1-battle.txt`へ記録。
  11,000フレーム目に、モンスターの残像がなく、全員の名前・能力値・HP欄が戻った状態を画面確認しました。
  宝箱操作の再現を確認したスクリプトではありません。

診断用の`--capture ROM BMP フレーム数 入力スクリプト [検証用セーブのコピー]`は、
ウィンドウやユーザー保存を使わず、既存コアの画面をBMPへ保存します。
フレーム数を`7500,9000,11000`のように並べると、同じ再生から複数時点を取得できます。

参照コア自体の実機完全互換を証明する検査ではありません。
報告された戦闘→宝箱の場面、長時間の描画、全イベントは個別の再現検証が必要です。
安全な高速描画は未実装です。再導入前に、背景・OAM・画面切替の途中フレームを含む検証を行います。
