# 音楽・SEの解析と再生

2026-10-21：保存済みの解析HTMLと関連データは`reference/`でGit管理しています（パスはリポジトリ直下基準）。以下の生成・検証コマンドは従来どおり`output/`へ出力します。

## SEの再生確認（2026-10-20更新）

`$0602` の単発音声要求を解析し、PRGバンク02・CPU `$A268` の参照テーブルにあるID 1〜13を、原作ドライバーと同じJSNES 2.1.0で再生した。

```powershell
node tools/probe_se.mjs
```

`reference/audio/se/index.html` で13種類を試聴できる。各 `se-01.wav`〜`se-13.wav` は約3秒の確認用音声。ヘッダーは `$A284`〜`$A2B0` で、チャンネル数1または2と演奏ポインターで構成される。`$8594` で要求を消費し、`$8597` 以降でテーブルを参照する。

全13件の要求消費、ヘッダー・全ストリーム先頭の実読込み、異なる非無音の音声、3秒以内の再生チャンネル停止を確認した。測定した停止は要求後4〜70フレームで、実機録音との一致は未検証。ROM位置、音声測定値、終了フレームは `output/audio/se/catalog.json` に記録する。

BGMを止め、場面側からの新しい音声要求を遮断した上で、`$0602` に選択番号を一度だけ設定する。音源ドライバーによる要求のクリアは通す。CPU・Mapper・APUの独自実装は追加していない。

各SEの正式名称・ゲーム中の使用場面、BGMとの同時再生・優先順位、探索UIへの接続は未確認。`$0601` / `$A112` の別系統5件は未分類で、今回の13種類を全効果音と断定しない。

## BGM検出・再生（2026-10-20更新）

Wiz1の13曲分のBGMヘッダーと39本の演奏ストリーム先頭を検出し、既存エミュレーター **JSNES 2.1.0** で音声を生成できるようにした。CPU・PPU・MMC1・APUはJSNESをそのまま使用し、独自音源は実装していない。

```powershell
node tools/build_audio.mjs
```

生成先は `output/audio/index.html`。HTMLにROMとエミュレーターを埋め込んでいるため、ブラウザーで直接開ける。曲選択、再生、停止、音量変更に対応。BGMの長さは固定せず、原作ドライバーを実行し続ける。タブを非表示にすると停止する。生成済み音声は `bgm-01.wav`（約30秒）と `bgm-02.wav`〜`bgm-13.wav`（各約10秒）。WAVは試聴用の抜粋で、曲全体や継ぎ目のないループ素材ではない。

### 検出根拠

- PRG 16 KiBバンク02、CPU `$8687` がBGM参照テーブル。ID 0は停止用でポインターとして解釈しない。ID 1〜13のヘッダーは `$86A3`〜`$86F7`、7バイト間隔。
- 各ヘッダーはチャンネル数3と、3本の16ビット演奏データポインターからなる。ROMファイル位置は `16 + 2 * $4000 + (CPUアドレス - $8000)`。
- バンク02の `$8509/$850E` で曲を選択し、`$8515` 以降でヘッダーを読み込む。`$835A` のデータ読込処理で各ストリーム先頭が実際に読まれることをJSNES実行で照合した。
- `$0600` はBGM要求、`$0604` は処理済み番号。入力なしの通常起動では177フレーム目にID 1が要求される。
- `$A112` と `$A268` に別の参照テーブルがある。BGMの13曲には含めない。`$A268` の13種類については上記SE再生確認を参照。

### 接続方法と検証

`web/audio/driver.js` が対象ROMの構造を検証し、原作を600フレーム動かして初期化した後、BGM要求を切り替える。タイトル側が曲1を再要求するため、試聴中はゲーム場面からのBGM・他音声要求を遮断する。一方、音源ドライバー自身の `$8344: STA $0600` による終了要求は通す。ROM本体とJSNESのコードは変更していない。音源の更新頻度やAPUの合成はJSNESの通常実行に従う。

ビルド時にSHA256を固定確認し、全13曲について原作によるヘッダーと全39ストリーム先頭の読込み、音程更新、有限かつ非無音の音声、クリッピングなし、13種類の異なるWAVを確認する。さらに曲1の再初期化後の先頭60フレームが同一PCMになることを検証する。測定結果とROM位置は `output/audio/catalog.json` に保存する。

ブラウザーでも曲1の再生、停止、曲13への切り替え・再生状態を確認し、ブラウザーのエラーログなし。実機録音との聴き比べ、正確な曲名・場面対応、全曲の末尾・ループ境界、Wiz2・Wiz3、探索プロトタイプとの接続は未検証。SEは上記の別検証を実施。

### 採用実装

JSNESはJavaScriptで動き、NodeでのWAV出力と既存のWebプロトタイプの両方で利用でき、MMC1とAPUを含むため採用。`third_party/jsnes/` に公式npmの2.1.0を固定し、npmのSHA512 integrityを照合して取り込んだ。バージョン、元リビジョン、取得URLと整合性情報は `PROVENANCE.json`、ライセンスは `LICENSE`、著作者一覧は `AUTHORS.md` に保持。生成HTMLにもライセンスと著作者一覧を表示する。

- [JSNES公式リポジトリ](https://github.com/bfirsh/jsnes)
- [採用リビジョン](https://github.com/bfirsh/jsnes/tree/cbad9f1db57dfb275b90ffa26f9c479c355d8d5c)
- [Apache-2.0ライセンス](https://github.com/bfirsh/jsnes/blob/cbad9f1db57dfb275b90ffa26f9c479c355d8d5c/LICENSE)

## ROM実行で確認したこと

既存の近似6502/MMC1実行に、APUレジスター書き込みの記録を追加した。

```powershell
python tools/trace_audio.py .nes/wiz1.nes --frames 600
```

結果は `output/audio/trace.json`。入力なしの起動から600フレームで5,271件の書き込みを記録。フレームは1始まりで、正確な実機時刻を保証しない。

|場所（16 KiB PRGバンク / CPUアドレス）|確認内容|
|---|---|
|02 / $8477〜$8486|$4017=$C0、$4015=$0F、$4010=$00、$4011=$00の初期化|
|07 / $C0C1〜$C0F3|RAMの音源状態をAPUへ送るループ|
|02 / $8061|$4011への直接出力値の書き込み|

固定バンクの送信ループは `$06E0` を `$4015` へ、`$06C8+Y` を `$4000+Y` へ送る。Yは0,4,8,12。`$06DC+X` が非ゼロなら、そのフラグをクリアし、`$06CA+Y` と `$06CB+Y` を `$4002+Y` と `$4003+Y` へ送る。

600フレームでこのループの `$4015` 書き込みは574回。最初の音程レジスター更新は177フレーム目で、矩形波2系統と三角波が更新される。矩形波1の音程下位は26回、矩形波2は14回、三角波は10回更新された。今回の範囲では `$400E/$400F` や `$4012/$4013` への書き込みは観測していない。ゲーム全体でノイズやDMCを使わないという意味ではない。

JSONの `pc` はpy65が書き込み時に保持していたPCで、命令先頭ではない。例えば `C0E4` のイベントは `$C0E3: STA $4002,Y` に対応する。表の命令位置は逆アセンブルで確認した。

## 再生までの見通し

原作の音源状態を生成する処理と、APUへ渡す境界が確認できたため、調査の足掛かりはできた。RAM更新元を辿って曲・SEの開始要求、データ参照、停止・ループ条件を特定するのが次の段階。

再生方式は、原作ドライバーを6502上で動かしてAPUで合成する方法と、解析した演奏データを独自プレイヤーで再生する方法を比較できる。現時点では前者が原作処理を残せる候補だが、バンク切替、呼び出し頻度、必要なRAM初期化の検証が必要。

このログは音声ではない。APUのステータス読み出し・IRQ・DMC DMA・波形合成は未実装で、CPU/PPUタイミングも近似。試聴、原作との音の一致、曲名・SE番号・ゲーム場面との対応、探索UIへの接続は未検証。完成までの工数はまだ確定できない。
