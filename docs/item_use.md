# アイテム使用後の変化とSP状態遷移

2026-10-21：保存済みの解析HTMLと関連データは`reference/`でGit管理しています（パスはリポジトリ直下基準）。以下の生成・検証コマンドは従来どおり`output/`へ出力します。

`tools/item_use_rules.py` に、ROM/CPUを必要としない変化判定と一部SPの状態遷移を追加した。抽出JSONの `use_rules` には判定式・変化先・元ルーチン位置を保存する。閲覧ページの「使用後の変化」から確認できる。

## 確認できた判定

rは乱数ルーチンの返す0〜255のバイト、tはアイテムの `break_raw`。確率の百分率ではない。

|経路|変化する条件|乱数を呼ぶか|変化時の所持品フラグ|
|---|---|---|---|
|I 通常使用・SP|t=255なら必ず、それ以外はr<t|t=255のとき呼ばない|flags OR 0x20|
|II 通常使用|t=255なら必ず、それ以外はr<t|t=255のとき呼ばない|flags OR 0x20|
|III 通常使用|t=255なら必ず、それ以外はr<t|t=255のとき呼ばない|flags OR 0x20|
|II SP|r≤t|必ず呼ぶ|(flags AND 0x40) OR 0x20|
|III SP|r≤t|必ず呼ぶ|flags AND 0x60|

通常使用のt=0は変化しないが、II/IIIのSPのt=0はr=0の場合に変化する。t=255は両経路とも必ず変化するが、乱数消費が異なる。独自実装で乱数列の順番を再現したい場合も分けて扱う必要がある。乱数バイトの一様性・ゲーム全体での確率分布は未検証。

所持品フラグは本段階では生値で扱う。通常使用の変化で0x80をここで消す処理はないが、II/IIIのSPでは消す。0x20もIIIのSPで新たに立てる処理はない。後続の完全な装備再計算をこの判定に混ぜない。

変化は指定された別アイテムIDへの置換。ID0も有効な「こわれたアイテム」等のレコードで、所持数を1減らす処理ではない。

## 元ルーチン

|作品|通常使用の比較部分|SPの職業判定|SPの乱数比較部分|
|---|---|---|---|
|I|bank6 BF9D|bank6 B675|効果後にB6E2→BF73を経由してBF9D|
|II|bank13 B348|bank13 B1AB|bank13 B1E7|
|III|bank13 B19A|bank13 AFFF|bank13 B03B|

SPは職業ビットがアイテムの装備可能マスクに含まれる必要がある。IはSP値0と符号ビットが立つ値も除外する。II/IIIは本ROM中の非0 SPアイテムを対象に、職業8種類を確認した。呪い・鑑定状態を含めた全メニュー入口の発動可否を保証するものではない。

IはSP効果を実行してから使用後の変化を処理する。II/IIIは発動確認後にアイテムを変化させてから、**元のアイテムのSP**を実行する。変化先がID0でも元のSPが消えるわけではない。

## 最大HP増加SPのCarryを解決

前回は効果本体だけを呼んだ際に、入力Carryによって+1/+2になることまで確認していた。今回は比較後の本来の呼出先まで実行した。

- II: 比較のCarryが効果本体まで残る。r<tで+1、r≥tで+2。変化条件はr≤tなので、r=tでは「変化する・最大HP+2」、r>tでは「変化しない・最大HP+2」。
- III: 比較後にED4Aのインラインディスパッチを経由し、Carryがクリアされる。この経路の最大HP増加は+1。

いずれも最大HPの上限は32767。II/IIIの実際の手裏剣について、全256乱数値とフラグ8パターンを使い、発動後の経路を照合した。キャラクターの現在HPはこのSP本体では増えない。IのSP22は別コードで、現在・最大HPを両方増やすが、今回の `resolve_sp` には未実装。

## 共通実装の使い方

`replacement` は、通常使用またはSPについて変化したか・変化後ID・フラグ・乱数消費の有無を返す。通常の使用呪文そのものは呼び出さない。

`resolve_sp` は、発動確認が受理された状態から、職業判定、実装済みSP効果、アイテム置換をまとめた新しいキャラクターを返す。引数のレコードは変更しない。未実装のSP効果なら状態を変更せず例外とする。

```python
import json
from pathlib import Path
from item_use_rules import resolve_sp

data = json.loads(Path('reference/wiz2/items_spells/data.json').read_text(encoding='utf-8'))
character = bytearray(128)
character[0x0a] = 7 << 2            # 職業: 忍者
character[0x1f:0x21] = (100).to_bytes(2, 'little')  # 最大HP
character[0x4b] = 105              # 所持枠0: 手裏剣
result = resolve_sp('wiz2', character, data['items'][105], roll=128)
# 本体は元の手裏剣のSP22。最大HP102、所持枠0は変化先ID0。
```

選択枠は0〜7。Iのフラグ/ID配列はキャラクター内4C/54、II/IIIは43/4B。II/IIIの原作は作業配列40/48を先に変え、あとからキャラクターへ書き戻す。共通実装では返すキャラクターに選択枠を書き戻した形を返し、検証側でもこの書き戻しを正規化して比較する。所持数、派生戦闘パラメータの再計算は別。

## 検証

`verify_item_use.py` はROMを書き換えず、実際の乱数ルーチンも実行する。初期乱数状態を設定し、指定した乱数バイトを返すようにしている。確認UIだけは実行せず、その手前で読み取られた変化設定と本来の戻り先を保って、受理後のコード位置へ進める。

合計273,864ケース:

- 通常変化268,032: 349アイテム×全256乱数値×フラグ3パターン。変化したID・フラグ・乱数消費、II/IIIの元の使用呪文IDを照合。
- 職業条件1,064: Iの101品×8職業、II/IIIの非0 SP品×8職業を照合。
- 実装済みSPの連続状態遷移4,768: フラグ全8組合せ、判定境界の乱数値、SP22は全256乱数値で比較。

出力は各作品の `items_spells/use_verification.json`。全件数はルーチン比較のケース数であり、ゲーム全体の再現率ではない。

```powershell
python tools/analyze_roms.py --verify
python tools/verify_item_use.py .nes/WIZ3.NES
python -m unittest discover -s tests
```

残る範囲: 通常使用を選べる場面・所持品状態、UIの確認/取消、使用呪文の実行全体、未実装SP本体、使用後の派生パラメータ再計算。今回の実装は「使えるか」のメニュー全体を代替するものではなく、確認後の状態遷移を先に切り出したもの。
