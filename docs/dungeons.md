# 3作品のダンジョン解析

2026-10-21：保存済みの解析HTMLと関連データは`reference/`でGit管理しています（パスはリポジトリ直下基準）。以下の生成・検証コマンドは従来どおり`output/`へ出力します。

対象は`rom_profiles.py`でSHA256を確認した3本です。Wiz1の10階層、Wiz2・Wiz3の各6階層、合計22階層・8,800マスを抽出しました。
各階層は20×20。表示名の「階層 N」はROMの番号であり、作品ごとの地上・地下の表記に置き換えていません。

## 出力と使い方

```powershell
python tools/analyze_roms.py --verify
```

共通入口は`reference/index.html`。各作品の`dungeons/index.html`には次の機能があります。

- 階層の切り替え、東・北の座標を指定したマスの選択。
- ダークゾーン、玄室、イベント表示の切り替え。
- Wiz2/3の玄室管理IDの色分け。
- 階段・座標移動の行き先の確認と、移動先マスへの表示切り替え。
- 方向別の壁値・生データ・元ROM位置の確認。
- 各階層のSVG、PNGの出力と、共通`maps.json`。

PNGは全体構造を見るための簡易プレビューで、イベントを色の点で示します。
SVGとビューアは座標・S（階段）・T（座標移動）・?（未分類）の記号を表示します。

## 座標と壁

マスの格納順は `y × 20 + x`。Xは東へ、Yは北へ増え、左下が(0,0)です。
四方の隣接座標は20を法として循環します。端の向こうにも通路や扉があるので、外周を強制的に閉じません。

壁の1 byteは、下位から北・東・南・西の順に各2 bitです。

| 値 | 表示 |
|---:|---|
| 0 | 通路 |
| 1 | 壁 |
| 2 | 扉 |
| 3 | 隠し扉 |

Wiz1のCPU `$D43E` のマスク `03 0C 30 C0`、移動処理と描画を手掛かりに確認しました。
双方のマスの値が異なる境界もあるため、片側の値へ統合しません。JSONには各マスの四方の値と`asymmetric_edges`を保存します。
ビューアは非対称の境界をマスの内側へずらして双方描画します。片方向壁の実際の移動処理・条件分岐は今後のゲーム実装で扱います。

## Wiz1の領域

16 KiB PRG bank 4（file `0x010010`）に以下のポインタ表があります。

| 内容 | CPUの表 | 参照方法 |
|---|---|---|
| 壁400 bytes | `$805C` | 表 + 階層番号 × 2 |
| マスフラグ400 bytes | `$8070` | 同上 |
| イベント定義64 bytes | `$8084` | 同上 |

すべてリトルエンディアンのCPUアドレスです。表から実際の位置を取得し、米国版の固定データ位置を流用していません。
フラグbit7は玄室、bit6はダークゾーン、bit5はイベント定義への参照です。
イベントの参照番号は下位4 bit。定義は16個×4 bytesで、`type, p1, p2, p3`です。

## Wiz2・Wiz3の領域

8 KiB PRG bank 9（file `0x012010`）の先頭に階層ごとのポインタ表があります。
各階層は1,200 bytesで、壁400 bytes、フラグ400 bytes、玄室管理データ400 bytesの順です。
フラグの上位3 bitはWiz1と同じ扱いで、イベント番号は下位5 bitです。
番号0～15は4 bytesの定義を参照し、16～31は通常の定義を経由しないマス内コードです。

イベント定義は初期値をROMからSRAMへコピーし、ゲーム中に変更します。

| 内容 | Wiz2 | Wiz3 |
|---|---|---|
| 初期化処理 | PRG bank 4、CPU `$844D` | PRG bank 4、CPU `$8433` |
| ROM初期値のポインタ位置 | file `0x008549` | file `0x008548` |
| ROM初期値の先頭 | file `0x00854B` | file `0x00854A` |
| SRAM格納先 | `$6B88 + (階層−1) × 65` | 同左 |

各SRAMレコードは定義64 bytesと検査値1 byteです。図ではROM初期状態を表示します。
玄室管理データは`$7500`以下の状態管理配列を参照するIDです。
読込処理の範囲外の値はWiz2では30、Wiz3では0へ置き換えられます。生値は`area_raw`にも残しています。

## 意味を特定したイベント

| イベント | Wiz1のtype | Wiz2のtype | Wiz3のtype |
|---|---:|---:|---:|
| 階段（確認画面を経由した座標移動） | 0 | 2 | 1 |
| 座標移動 | 2 | 10 | 2 |

これらの3パラメータは、移動先の東座標・北座標・階層番号です。階層0は城への帰還です。
範囲内の移動先だけ`destination`としてJSONへ追加します。
他のイベントは値を失わず「未分類」とし、NPC、罠、メッセージ、アイテム要求などの意味を推測で埋めていません。

## ROM処理との照合

`verify_dungeons.py`は以下の実ROMルーチンを実行して、全8,800マスの壁とフラグを比較します。

| 内容 | Wiz1 | Wiz2 | Wiz3 |
|---|---|---|---|
| マス読込 | bank 4 `$8000` | bank 13 `$A469` | bank 13 `$A936` |
| 玄室ID読込 | 別層なし | bank 13 `$A2D9` | bank 13 `$A7A6` |

Wiz1はイベントマスの定義4 bytesも比較します。
Wiz2/3はイベント初期化ルーチンを実行してSRAMの全6階層×64 bytesを比較し、各マスの玄室管理IDも比較します。すべて一致しました。

```powershell
python -m unittest discover -s tests
node tests/check_dungeon_ui.cjs
```

SVGのXML構造、各階層400個の選択領域、マスの選択、階層切り替え、行き先表示、レイヤ切り替えを検証します。
JavaScriptはオフラインで実行します。ブラウザ自動操作はローカルファイルURLの制限があるため未実施です。
PNGの全体図を目視確認しています。
