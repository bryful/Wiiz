# 原作処理から独立させた小さなルール実装

2026-10-21：保存済みの解析HTMLと関連データは`reference/`でGit管理しています（パスはリポジトリ直下基準）。以下の生成・検証コマンドは従来どおり`output/`へ出力します。

`tools/game_rules.py` はCPUエミュレーターを使わず、抽出済みのアイテムと状態から結果を計算する。`rule_data.py` はROM別のSP処理表・AC呪文・基本回復呪文を抽出し、各作品の `items_spells/data.json` に追加する。

ゲーム全体の実装ではなく、原作の部分ルーチンと照合できた計算単位。装備の可否、初期能力値、レベル・職業の基礎攻撃回数、SP発動可否、アイテム変化、ターン進行は含まない。

## 装備済みアイテム1品の加算

|作品|CPUルーチン|処理の違い|
|---|---|---|
|I|bank6 AFBA|属性が合えばAC補正と攻撃力を加算。合わなければAC+1・攻撃力−1・クリティカル値0。武器の攻撃回数は現在値との最大値|
|II|bank13 B435|攻撃力を8ビット加算。武器の攻撃回数も加算し、符号ビットが立つか0なら1、正値は最大10|
|III|bank13 B266|IIと同じ攻撃回数処理。攻撃力は8ビット加算後に符号ビットが立てば0にする|

3作品とも、武器のダイス個数・面数を設定し、ダメージ加算値は8ビットで累積する。II/IIIではこの部分ルーチンにAC処理がないため、ここでACを加算しない。属性不一致時のII/III全体の扱いは未再実装。

以前のJSONの `minimum_attacks` は互換のため保持しているが、II/IIIでは「最低値」ではなく**攻撃回数に加える値**。この名称を基に共通のmax計算を実装しない。

IのAFBAが変更する防御・倍打のビット列は、実装対象の出力比較から除外している。完全な装備再計算には、これらと所持品だけで働く効果も必要。

使用例（抽出したJSONから計算。ROMやpy65は不要）:

```python
import json
from pathlib import Path
from game_rules import equipment_contribution

data = json.loads(Path('reference/wiz3/items_spells/data.json').read_text(encoding='utf-8'))
state = dict(strength=0, attacks=1, ac=10, critical_raw=0,
             damage=dict(count=2, sides=2, bonus=0))
result = equipment_contribution(data['game'], state, data['items'][86])
# 村正: damage=10d5、strength=8、attacks=4。
# この関数は職業制限を判定しない。装備が有効になった後の寄与だけを計算する。
```

## ACを変える呪文

3作品で10種ずつを解析。JSONの `effect.kind=ac_modifier` に、補正値・味方側が唱えた際の対象・戦闘中の効果であることを記録した。

|呪文|ACへの加算|対象（味方側の詠唱）|
|---|---:|---|
|MOGREF|−2|術者|
|SOPIC / PORFIC|−4|術者|
|DILTO|+2|敵1グループ|
|MORLIS|+3|敵1グループ|
|MAMORLIS（IIIのROM表記はMAMORILS）|+3|敵全体|
|KALKI|−1|味方全体|
|MATU|−2|味方全体|
|MASOPIC / BAMATU|−4|味方全体|

`modify_ac` は−99〜99に収める。各作品で入力AC全199値×実際の補正5種を原作コードと照合した。さらに各呪文のハンドラーそのものを実行し、どの戦闘配列要素が変わるかを照合。Iの味方全体は6スロット、II/IIIは現在のパーティ人数に従う。敵側の詠唱や戦闘前の発動チェックは未照合。

## 基本回復

DIOS=1d8、DIAL=4d4、DIALMA=8d3を**各作品のコードから**確認。慣例的な呪文説明で置き換えない。各作品の実ハンドラーが設定した値もCPUで照合した。

`heal_hp` は振った後の回復量を受け取り、状態コード5以上には効果を適用せず、最大HPまで回復させる。II/IIIでは乱数計算直後から原作の対象・状態判定・HP加算を実行し、状態8種類、HPのバイト境界・最大値付近、回復量0〜255の代表値を比較した。Iはダイス設定までの照合で、HP更新の実行比較は未追加。乱数分布・呪文の発動条件はこの検証とは別。

## SP

処理表は以下の位置。全エントリーについて、原作のディスパッチを実行し、抽出したハンドラーに到達することを確認した。

|作品|ポインター表のROM位置|エントリー数|
|---|---|---:|
|I|0x1B6FE|24|
|II|0x1B02E|31|
|III|0x1AFC3|28|

`special_power_core` は発動後の単体キャラクター効果のみ。キャラクターの格納形式を完全に解読したわけではないため、状態は生バイト列とし、変更する位置をJSONに保存する。未実装の効果は例外とする。

- IのSP1はちからを上限18まで+1、SP17は職業値を忍者へ。SP22は現在・最大HP+1、SP23は状態コード5未満の仲間のHPを最大値へ戻す（この2つは説明のみで共通コアは未実装）。
- IIのSP1〜6は能力値を上限18まで+1、SP7〜12は下限0まで−1、SP17は忍者へ。SP22は最大HP増加、SP23は仲間のHP回復。
- IIIのSP1〜6は種族別上限まで+1。固定領域DC0Bの種族初期値表+10が上限。5種族・6能力について原作のDBEBを含めて照合。SP7〜12は下限0まで−1、SP13は年齢格納値が20以上なら−1（単位未確定）、SP16/17は職業ビットを君主/忍者へ、SP20は状態コード6へ。SP22/23は最大HP増加/仲間のHP回復。

II/IIIのSP22は`ADC #1`の前に`CLC`がない。効果本体への入力Carryが0なら+1、1なら+2で、結果は32767が上限。`special_power_core` を直接使う場合は `carry_in` の明示が必要。追加解析で、IIは発動時の乱数比較のCarryを保ち、IIIはディスパッチでCarryをクリアすることを確認した。発動確認後の経路を含む実装は `item_use_rules.resolve_sp`、詳細は [item_use.md](item_use.md) を参照。

SPの処理本体が共通の復帰先を指すものは `no_effect_body` として区別する。発動時のアイテム変化まで「何も起きない」という意味ではない。IIIのSP19（BCD演算を含む）、24〜27（乱数や複合処理を含む）、IIの28〜30（イベント系）は引き続き未解析。

## 検証・残る範囲

```powershell
python tools/analyze_roms.py --verify
python -m unittest discover -s tests
node tests/check_item_spell_ui.cjs
```

追加した `rules_verification.json` は元ルーチンとの比較件数とSHA256を保持する。合計5,590ケース:

- 装備寄与1,653ケース（Iは各アイテム×3属性×3状態、II/IIIは各アイテム×3状態）
- AC加算2,985ケース、AC呪文の対象30ケース
- SP本体590ケース、SPディスパッチ83ケース
- 回復ダイス設定9ケース、II/IIIのHP更新240ケース

これは原作全体の一致率ではない。状態異常の付与・自然回復、攻撃呪文の抵抗・成功率、使用場面の判定、所持効果、基礎能力の再計算を残している。SP職業条件・使用後のアイテム変化・一部SPの連続処理は [item_use.md](item_use.md)、状態表示・治療・蘇生と必要な乱数処理は [status_rules.md](status_rules.md) に追加の検証結果を記録した。
