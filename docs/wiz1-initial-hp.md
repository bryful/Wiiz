# Wiz1 新規ロードの最大HPが0になる原因

2026-10-21。ユーザー報告：新規ロード、Max creation bonus OFF、Wiz1 bug Fix ON、
保存して読み直したときに最大HP0を確認。ターボファイルも使用。

## 確認した事実

ローカルの通常保存先を読取専用で調査し、`wiz1.sav` の名簿1番に
職業6（ロード）、レベル1、最大HP0、現在HP1、全能力18のレコードを確認。
同じレコードが最大HP0・現在HP0の状態で既存バックアップにも残っていた。
データの修復・上書きやアプリの動作変更は行っていない。

原因を再現する入力が原作の新規作成処理に存在する。保存読込やターボファイルを
介さずに最大HP0・現在HP0を生成するため、これらを使わなくても発生する。
今回の記録だけから、ユーザーが最初にどの順序で設定・保存・転送したかまでは断定しない。

## 原作の初期HPテーブルの範囲外参照

日本版PRG bank6の命令列：

```asm
A27F LDX $0252         ; 職業0～7
A282 LDA $A315,X       ; 乱数の上限
A285 JSR $CDDA         ; 0～上限-1の乱数
A288 CLC
A289 ADC $A31B,X       ; HP基本値、8ビット加算
A28C LDY #$22
A28E STA ($2E),Y       ; 最大HP下位
A290 LDY #$20
A292 STA ($2E),Y       ; 現在HP下位
```

初期化でHP上位バイトは0になっている。HP用テーブルは通常作成対象の6職分しかない。

|職業|乱数上限として読む値|基本値として読む値|生成するHP|
|---|---:|---:|---|
|戦士|7|8|8～14|
|魔法使い|5|2|2～6|
|僧侶|7|6|6～12|
|盗賊|5|4|4～8|
|司教|5|4|4～8|
|侍|7|12|12～18|
|ロード|8（戦士HP基本値の流用）|255（後続の呪文初期化テーブル）|255、0、1、2、3、4、5、6|
|忍者|2（魔法使いHP基本値の流用）|14（後続テーブル）|14～15|

ロードは `255 + 乱数0～7` の下位8ビットだけを保存する。
乱数1なら `255+1=256→0` となり、最大HP・現在HPがともに0になる。
乱数0なら逆に255になる。生命力による補正や設定ON/OFFの判定はこの命令列にない。

## 再現

既存のpy65 1.2.0と既存解析用メモリー配置を使い、上記命令列と原作乱数を実行。
`tools/analyze_creation_hp.py` → `output/creation-hp-analysis.json`。
乱数内部状態 `$0040=$20, $0041=$00` はHP0の具体的な再現入力。
全65,536状態のロードHPは、0～6と255に各8,192状態ずつ分布する。
これはこの処理直前の内部状態を等重みで列挙した結果であり、UI操作を含む実プレイの
乱数状態分布が均等であることまで検証したものではない。

通常版・パラメータ変更版の初期HP処理で再現する。
2011年 `wiz1patch.ips` 適用前後で `$A27F～$A328` の処理・テーブルが同一であることも確認。
追加した商店パッチ2本もこの領域を変更しない。
従って現在のWiz1 bug Fixの8項目にはこの不具合の修正は含まれていない。

## Max creation bonusとの関係と検証漏れ

原作の通常ボーナスだけではロードの新規作成に必要な能力値に届かないため、
このテーブル欠落が通常の作成では表面化しにくい。
最大ボーナス機能等で新規ロードを作成可能にすると表面化する。
設定をOFFにしても、既に生成された割り振りポイントや登録済みHPは元に戻らない。
ユーザーの実際の作成時の設定履歴は不明であり、報告されたOFFを否定するものではない。

既存 `creationCheck` は全種族の割り振り・登録・再読込を確認するが、職業選択では
先頭候補を使い、全職業の初期HPを検証していなかった。このため新規ロードの異常を見逃した。
先行する `reference/patch/fc` の石垣環マンガ版メモにも、ロードの初期HPが255になる原因として
同じ6職分のテーブル不足が説明されている。今回は0になる側をROM命令実行と保存実体で確認した。

## 原因解析時の範囲

原因解析のみ。HPを一律1以上へ丸める等の動作変更、既存キャラクターの回復・修復は未実施。
ロードの妥当な初期HP仕様を決めることと、既存レコードの修復値を決めることは別途必要。
ターボファイル全転送経路や、保存時にHP1へ変化した経緯は今回の再現検査の対象外。
新規CPU/Mapperの実装や外部コードの追加取り込みはしていない。

## 改善実装（2026-10-21）

ユーザー指定に従い、**新規作成時の初期最大HPが15以下なら、最大HP・現在HPを15**にする。
Wiz1の全職業に共通適用し、最大HP16以上（ロードの255を含む）はそのまま。
Wiz1 bug Fixや最大ボーナスの設定とは独立して、確認済みWiz1で常時適用する。
既存キャラクター、戦闘中のHP減少、転職・転送・ロード時のHPは補正しない。
既存の最大HP0キャラの自動修復は行わない。Wiz2/3には適用しない。

既存binjnesのRAM書込コールバック（既存の作成ボーナスと同じ接続方式）を再利用。
原作の乱数・職業別HP計算は維持し、bank6の`$A292: STA ($2E),Y`が終わる瞬間
（コールバックPC `$A294`）のみ、保存済みの初期最大HPの上位・下位を読み判定する。
書込先は名簿20枠の現在HP下位に限定し、該当するときだけ現在・最大HP下位を15へ変更する。
この時点では原作のチェックサム・ミラー生成前なので、原作の登録処理をそのまま使える。
未知のコード改訂には`Session`が確認済みプロファイルを設定しないため適用しない。
上流エミュレーター、CPU、Mapperの変更や新規依存の追加はない。

`tests/check_native_initial_hp.py` は通常版とパラメータ変更版を対象に、既存binjnesで
原作HP書込命令を20枠×256入力で実行し、0～15→15、16～255→そのままを検査する。
同じHPフィールドへの作成処理外からの0書込が補正されないことも検査する。
この部分検査はNMIタイミングを除外したCPUテストであり、通常のゲーム操作では使わない。
追加の`--creation-hp-check`は原作メニューで全5種族のロードを作成し、
バグ修正ONで初期HP15以上・現在HPとの一致・登録・保存再読込を確認する。
他職業の全UI経路とAndroid実機操作は未検証。
