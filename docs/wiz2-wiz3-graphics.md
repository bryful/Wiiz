# Wizardry FC II / III の画像解析

2026-10-21：保存済みの解析HTMLと関連データは`reference/`でGit管理しています（パスはリポジトリ直下基準）。以下の生成・検証コマンドは従来どおり`output/`へ出力します。

`.nes/WIZ2.NES` と `.nes/WIZ3.NES` の実データを解析した結果です。ここでのII/IIIはROMファイルの区分です。

| 項目 | WIZ2.NES | WIZ3.NES |
|---|---|---|
| SHA256 | `6b1d9ca5bbe9be4f7d12c2de2dd8115f99c1cc2de3944787d2d5c2959cc116c0` | `b5f7dff95724e1a9f5c486b15f53aae4124266c18abb1218a48a73a539149212` |
| サイズ | 262,160 bytes | 262,160 bytes |
| Mapper | 4 / MMC3 | 4 / MMC3 |
| PRG / CHR | 各128 KiB | 各128 KiB |
| CHRタイル | 8,192 | 8,192 |
| モンスターID数 | 78 | 90 |
| 確定・不確定のケース数 | 156 | 180 |
| 共有除外後の配置数 | 105 | 114 |
| ROM処理との照合 | 全156ケース一致 | 全180ケース一致 |

Wiz1のMMC1・16 KiB PRG切り替えに対し、両ROMはMMC3の8 KiB PRG切り替えを使います。
Wiz1の配置フォーマットを適用せず、描画命令を逆アセンブルして別形式を特定しました。

## 描画ルーチンとテーブル

| 内容 | Wiz2 | Wiz3 |
|---|---|---|
| 描画ルーチン | 8 KiB PRG bank 4、CPU `$9F00`、file `0x009F10` | 8 KiB PRG bank 11、CPU `$AAF2`、file `0x016B02` |
| 入力:モンスターID | `$028E` | `$02AE` |
| 入力:識別状態 | `$95`: 0=確定、非0=不確定 | 同左 |
| 不確定画像の参照表 | CPU `$9F9B`、file `0x009FAB` | CPU `$AB7C`、file `0x016B8C` |
| 画像オフセット表 | file `0x00C010` | file `0x016BE6` |
| 確定時の画像番号 | ID + 28 | ID |
| 不確定時の画像番号 | 参照表の値 / 2 | 参照表の値 |
| レコード基準位置 | file `0x00C110` | file `0x014010` |
| CHRバンク補正 | 32 | 48 |
| スプライト属性の初期値 | `$20`（背景より後ろ） | `$00` |

画像オフセットは16 bitのリトルエンディアンです。上位bitが1の場合、通常の描画処理は画像を出さず終了します。
Wiz2は描画時に論理PRG bank `$16` を選びますが、このROMの物理アドレス線ではbank 6を参照します。

## 配置レコードの形式

1. CHRバンク補正前の値（1 byte）。
2. 最初のタイル番号（1 byte）。
3. bit7=0の間、パレット値を0～12 bytes読む。
4. 続いて以下の座標ストリームを読む。

| token | 動作 |
|---|---|
| `0x00～0x7F` | X相対位置。現在Y・現在tile・現在属性でスプライトを1個生成し、tileを1増やす |
| `0x80～0xFD` | Y相対位置（下位7 bit）。現在Yを更新 |
| `0xFE` | スプライト属性を1増やす（主にパレットの切り替え） |
| `0xFF` | 終端 |

実行時の原点は `$C0/$C1`。今回は呼び出し元で観測した値としてWiz2は`$5C/$53`、Wiz3は`$04/$43`を使用しています。
画像は外接矩形で切り出すため、新規ゲームでは`bounds`の位置を使って配置し直せます。

パレットは `$F0～$FB` に1パレット当たり3色ずつ入り、PPU転送ルーチンが各パレットの先頭に`0x0F`を挿入します。
パレット値を12 bytes書かないレコードも多くありますが、通常は書かれた色だけが参照されます。
CHRはMMC3のR2/R3による1 KiB単位の2バンクを使用します。今回のデータでtileの最大値はWiz2が123、Wiz3が122です。
タイルごとの元ROM位置をJSONに保存しています。

## 特殊ケース・確認用画像の限界

- **Wiz2 ID59 Doppelganger（確定）**: 画像オフセットのbit15が1。通常ルーチンでは空です。出力は1×1の透明PNGとし、一覧に注記しました。ゲーム全体での変身などの特殊処理は未解析です。
- **Wiz3 ID34 No-see um、ID39 Evil Eye（ともに確定）**: スプライトが使う色の一部を当該レコードが書きません。それぞれスプライトパレット内インデックス6、11を直前の状態から引き継ぎます。現時点の画像は不足値を診断用の0で補い、一覧とJSONに明示しています。実行時にどの色になるかは未確定です。
- RGBは固定のNES色変換表です。実機の信号・機種差・エミュレータ設定を再現するものではありません。
- 画像はスプライトの重なり順を保って復元しますが、PPUの1走査線8スプライト制限による欠けや点滅は再現しません。

空ケースも含めて全ケースのOAM、ゼロ初期化RAMからのパレットバッファ、CHR指定、PRG復帰状態をROM処理と比較しています。
`mmc3_cpu_bus.py` はこのためのCPUバスであり、MMC3のPPU/IRQまで含むエミュレータではありません。
`trace_graphics.py` の起動・画面トレースは引き続きMMC1専用です。

## 名前

Wiz2はfile `0x014010` の78エントリのポインタ表から可変長モンスターレコードを参照し、先頭16 bytesのASCII名を取得しました。
Wiz3はfile `0x00C010` の90エントリのポインタ表からレコードを参照し、レコード内の確定・不確定名のポインタを辿ってNUL終端のASCII名を取得しました。
日本語名の元バイト列もJSONへ保存しますが、独自文字コードを含むため、今回の出力では日本語文字列としての確定デコードは行っていません。

## 再実行

```powershell
python tools/analyze_roms.py --verify
```

`reference/index.html` が3作品共通の入口です。py65は`requirements-analysis.txt`で導入します。
画像だけなら追加ライブラリなしで以下を実行できます。

```powershell
python tools/extract_monsters.py .nes/WIZ2.NES
python tools/extract_monsters.py .nes/WIZ3.NES
```

既定の出力先はROMのSHA256から選び、Wiz1の出力を上書きしません。
