# Wiz1日本版の遭遇テーブルと探索への接続

## 解析したROMの処理

米国版の[解析資料のROMマップ](https://taotao54321.github.io/appsouko/work/Game/Wiz1_NES/prog_rom.txt)を入口に、日本版ROMの命令列を調べ直した。米国版のアドレスをそのまま日本版へ適用していない。

日本版の固定バンク `$E104` 以降は `(階層−1)×15` を計算し、各階の5バイト構造体3件から1件を選ぶ。`$E131` が読むテーブルは CPU `$E26D`、iNESファイルオフセット `0x1E27D`。10階分150バイトある。最初の乱数の下位2ビットが非ゼロなら通常枠、ゼロなら次の枠へ進み、もう一度同じ判定を行う。独立な一様乱数なら各枠の比率は12:3:1となる。

各5バイトは `[base, step, repeats, width, threshold]`。`$E063` の抽選ヘルパーは乱数バイトがthreshold未満の間baseへstepを加え、最大repeats回繰り返し、最後に `[0,width)` の乱数を加える。

|地下1階の枠|生データ|出現する主グループの敵ID|
|---|---|---|
|通常|0,0,0,4,0|0〜3|
|次の枠|1,0,0,5,0|1〜5|
|最後の枠|3,0,0,3,0|3〜5|

`$E22B` はモンスターの出現数ダイスを振り、`min(階層+4,9)` で上限を制限する。地下1階の主グループは最大5体。今回のブラウザー実装ではこの出現数ダイスと上限を採用した。追加グループを作る処理は未接続。

## 照合

`python tools/verify_encounters.py` は30構造体それぞれについて乱数の2状態バイトを16×16通り設定し、日本版ROMの `$E063` と独立Python実装を照合する。敵IDだけでなく実行後の乱数状態も検証し、7,680ケース一致した。結果と抽出テーブルは `output/encounters/verification.json` と `encounters.json` に保存する。

さらに出現数決定ルーチン `$E22B` を全101モンスター×10階×8乱数状態で照合し、8,080ケース一致した。出現数と実行後の乱数状態を確認する。面数0では `$CDB8` が乱数を消費せず追加値を返す。ID94の出現数 `1d0+1` は1体となるため、ブラウザー側もその分岐を反映した。

これらは抽選・出現数ヘルパーの検証。遭遇を開始する状況の全分岐、玄室管理、友好判定、追加グループまでは照合していない。

## 探索版の仕様

- 自動遭遇は地下1〜10階。全101体の名前・画像・パラメータを同梱。遭遇する敵は移動先の階層テーブルから選ぶ。全101体が通常遭遇するわけではなく、固定イベントの敵などはまだ接続していない。
- 成功した移動だけで抽選する。最初の5歩は安全、その後は1歩ごとに1/8。戦闘開始・入口への帰還・保存読込・遭遇設定変更で安全歩数をリセットする。これは原作の遭遇率ではなく試作ルール。
- イベントのある移動先では自動遭遇しない。転移は移動先の階層とマスで判定する。旋回・壁への衝突・調べる操作では遭遇しない。
- 「歩行中に遭遇する」でオン・オフ。初期値オン。設定と安全歩数はセーブしない。
- 敵の対象選択が可能。全員攻撃は選択した敵から攻撃し、倒すと次の生存敵へ移る。生き残った各敵が反撃する。勝利経験値は倒した全員の合計を生存者で等分。
- ブラウザーは `Math.random` を使うため、ROMと同じ乱数列にはならない。範囲データはROM由来だが、原作の抽選結果との完全一致は主張しない。

`node tests/check_encounters.cjs` と `node tests/check_encounter_ui.cjs` で、歩行→集団遭遇→対象選択→呪文→勝利→保存→回復→探索継続を確認する。UI検証はDOMと描画のモックを使い、実ブラウザー表示は未検証。

`node tests/check_all_floor_encounters.cjs` は全10階で実ROMのマップを6歩進み、扉・階層別の敵・出現数上限・逃走・保存復元を確認する。抽選のサンプル10,000件が各階の出現範囲内であることと、全画像の同梱を確認する。UIテストでも全10階の保存読込→歩行遭遇→名前・画像の表示→逃走まで実行する。
